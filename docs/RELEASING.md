# Release procedure

[Home](../README.md) · [Русский](#русский)

1. Choose the release version. The first public beta is `1.0.0-beta.1`; internal v3 is its development ancestor.
2. Update `package.json`, lockfile root metadata, `src-tauri/Cargo.toml`, the local crate entry in Cargo.lock, Tauri config, window/page title and visible app version consistently. The `.irta` magic stays `IRTANT/2` unless its contract actually changes.
3. Update the current guides in English and Russian, field descriptions and generated docs. Append a dated changelog entry with fixes/features/compatibility and known limits.
4. Run the checks in DEVELOPMENT.md; verify startup, one file round trip in both modes, actual PNG/SVG files and the installers you intend to distribute. Record OS/runtime versions and results.
5. Resolve license and third-party notices; review staged files only. Exclude secrets, personal paths, chats, company documents, temporary output and proprietary reference executables. Embedded reference geometry and its provenance also need review.
6. Commit the approved source, create a tag such as `v1.0.0-beta.1`, and prepare a GitHub pre-release. Never call a beta a stable/certified calculation product.
7. Attach `rf-calc-VERSION-web.zip`, tested native packages only, and SHA-256 checksums. Source archives are generated by GitHub after the tag exists. Record unsupported/untested platforms explicitly.
8. Verify links and downloads. Only then publish. The validation workflow does not deploy a site or publish releases.

Keep installation and usage instructions version-independent where possible. Git tags preserve old documentation snapshots. For a breaking behavior change, explain migration in the changelog and current guide; do not create competing current manuals.

## Русский

1. Выбрать номер выпуска; первый публичный бета-выпуск — `1.0.0-beta.1`, внутренняя v3 — его основа.
2. Согласовать package/lockfile, Cargo.toml и запись проекта Cargo.lock, Tauri, заголовки окна/страницы и видимую версию. `IRTANT/2` меняется только при изменении контракта формата.
3. Обновить текущие EN/RU руководства, описания полей и генерируемые документы; добавить датированную запись истории с совместимостью и ограничениями.
4. Выполнить проверки, запуск, чтение/запись обоих режимов, реальные PNG/SVG и приёмку распространяемых установщиков; записать ОС/среду/результаты.
5. Выбрать лицензию, подготовить уведомления зависимостей и проверить только публикуемый состав. Исключить секреты, локальные пути, переписку, КД, временные результаты и чужие программы. Проверить также происхождение встроенных эталонных геометрий.
6. Зафиксировать утверждённый код, создать тег и предварительный релиз GitHub. Beta не называется стабильным или сертифицированным продуктом.
7. Приложить веб-архив, только проверенные native-пакеты и SHA-256; исходные архивы GitHub создаст по тегу. Явно перечислить непроверенные ОС.
8. Проверить ссылки/загрузки и только затем публиковать. Проверочный workflow не публикует релизы и не развёртывает сайт.

Общие руководства не размножаются на каждую версию. Старые снимки сохраняют Git-теги. Несовместимые изменения описываются в истории и актуальной инструкции миграции.
